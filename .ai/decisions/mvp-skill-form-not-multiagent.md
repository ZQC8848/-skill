# V1 以 Claude Skill 的形式发布，不是写代码的多 Agent 系统

**2026-08-21 ・ 状态：standing ・ 范围：只覆盖 v1 的实现形式；不决定这个产品未来会不会变成真正的 app**

## 是什么逼出了这个选择

原始设计（这个仓库存在之前，跟 GPT 一起想出来的）指定的是一套写代码的多 Agent 架构：结构化 JSON state、专门的 Signal Extraction Agent、带 confidence score 的人格假设、Strategy Agent、Outcome Learning 闭环。这是真正的工程量，在还不知道底层前提是否成立之前——即"持久化的关系状态 + 对方建模 + 结果反馈"是否真的比"一个普通 LLM + 聊天历史"效果更好——先把它搭出来,有可能是一次投入很大但没法证明值不值得的建设。

## 决定

V1 是一个 Claude Skill：一个 SKILL.md 路由 + 按需查阅的 reference markdown 文件 + 用纯 markdown 文件持久化的状态（`profiles/`、`self/`）——没有编排代码、没有 JSON schema、没有独立的 agent 进程。这跟 `Mayuqi-crypto/HowToGetAlongWithGirls` 是同一种实现模式，只是把范围从线下/长期关系换成 dating app/多 match。

## 为什么不选别的方案

| 备选方案 | 它的优势 | 为什么不选 |
|---|---|---|
| 现在就把完整的结构化多 Agent 系统搭出来 | 符合原始设计的野心；更好的作品集/工程故事；长远看是"正确"的架构 | 在核心假设（持久化状态+对方建模到底能不能真的提升建议质量）完全没被验证之前，先把最贵的部分砸下去。Fieldnotes 自己的原则在这里同样适用：不要搭建现在填不进内容的骨架。 |
| 原样照搬 HowToGetAlongWithGirls 的模式 | 已经跑通、验证过的 Skill 结构——风险低 | 它的范围（线下、长期/婚姻导向）和它的隔离模型（假设只有几个同时进行的对象）都不适合 dating app 的规模，也不适合这个产品想要的 MBTI/打分商业化包装——见隔离决策和 MBTI 决策。结构可以复用，内容和隔离模型不行。 |

## 这个决定依赖什么

| 假设 | 状态 | 证据，或能确定它的检查方式 |
|---|---|---|
| 一个 Skill（prompt + 文件）能在没有真正编排代码的情况下,充分模拟原始设计里的那几层（记忆、信号识别、策略） | 未验证 | 靠把 v1 搭出来、用真实聊天记录/真实多 match 场景测试来确定 |
| 真正值得验证的核心假设是"持久化关系状态有没有用"，而不是"更多 Agent 结构有没有用" | 已验证——这本来就是 GPT 在原始设计讨论里自己的表述 | — |

## 承担的代价

- v1 里没有结构化的 confidence score 或 JSON state——人格/兴趣信号是叙述性文字 + 一个展示用的分数，不是可查询的结构化对象。以后如果想在跨 match 层面做真正的数据分析，需要一次迁移，而不是直接读取。
- Outcome learning 是手动触发的一次性汇总（见 architecture.md），不是持续运行的 pipeline。

## 什么情况下会推翻这个决定

- 核心假设被验证成立（用户反馈持久化状态版本明显优于纯聊天历史的建议）**并且**产品需要真正的多用户并发、跨 match 的数据分析,或者基于文件的方案给不出的性能——到那时候，迁移到真正的后端，把多 Agent 设计当作 v2 架构重新考虑，而不是现在就做。
