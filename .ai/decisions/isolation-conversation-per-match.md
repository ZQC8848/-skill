# Match 之间的隔离是结构性的（一对象一对话），不是靠纪律维持的

**2026-08-21 ・ 状态：standing ・ 范围：覆盖同时进行的多个 match 之间的隔离；不覆盖这个用户和产品未来其他用户之间的隔离**

## 是什么逼出了这个选择

一个用户会同时经营多个 match。任何把一个以上 match 的数据同时放进同一个 context window 的设计，都存在把 A 的信号/历史错误归到 B 身上的可能——而且这种失败是无声的：不会报错，只是建议错了,而且会一直错下去,直到用户碰巧发现。

## 决定

每个 match 拥有自己独立的对话/线程，绑定自己的 `profiles/<id>.md`。任何一个对话都不会同时持有两个 match 的聊天记录或档案内容。唯一允许跨越 match 边界的通道是 `self/inbox.md`（已脱敏，不带可识别细节）和 `profiles/_index.md`（只有状态字段）——见 architecture.md。

## 为什么不选别的方案

| 备选方案 | 它的优势 | 为什么不选 |
|---|---|---|
| 单个对话，每轮通过重新读取不同的档案文件来切换上下文，每条回复强制带状态标签 | 用户摩擦更小（不用管理多个线程）；这是最初的方案 | 隔离效果依赖于模型*每一轮都可靠地遵守规则*——这是一个用户从外部无法验证的软约束。漏掉一次重新读取,就会无声地发生数据污染。放弃这个方案,选择一个不依赖纪律的保证。 |
| 每个 match 配一个完全独立、代码实现的 agent，有真正的进程/内存隔离 | 保证最强；符合原始（GPT 协助的）设计里"真正的"多 Agent 系统会怎么做 | 保证的方向是对的，但阶段不对——现在就搭自定义 agent 编排，比验证核心假设所需的工程量要大得多。一对象一对话已经能拿到同样的结构性保证（没有共享 context），而不用写编排代码。等这个项目真的变成有后端的产品时再重新考虑。 |

## 这个决定依赖什么

| 假设 | 状态 | 证据，或能确定它的检查方式 |
|---|---|---|
| 这个 Skill 运行的宿主环境支持用户低成本地为每个 match 开/命名一个新对话 | 未验证 | 取决于最终的产品形态；在 Claude Code / 任何支持多线程的聊天界面里目前成立 |
| Dating app 自己的收件箱本来就已经是"一个 match 一个线程" | 已通过实际检查验证 | 这是 Tinder/Bumble/Hinge 上通用的 UX，不是某一家特有的 |
| Dashboard/self-model 的需求能在从不跨 match 打开完整档案文件的前提下被满足 | 未验证 | 等 `_index.md` 的字段定稿并用真实的"该放弃谁"类问题测试过之后再确定 |

## 承担的代价

- 用户（或者最终产品的界面）要管理 N 个打开的线程，而不是一个——可以接受，因为这正好对应 dating app 自己收件箱的结构，而不是引入一种新的交互模式。
- 跨 match 的模式识别（"她让我想起 match B"）需要显式地走一次 self-model/dashboard 的往返，单个线程内部拿不到这个能力,不是免费的。

## 什么情况下会推翻这个决定

- 如果宿主环境无法低成本支持每个用户同时开很多线程（做真实 app 时发现的实际约束），应该转向带有更硬的、机器可检查的隔离机制（比如一个真实的、每次读写都要校验的 per-match state ID）的单会话设计，而不是退回到已经被否掉的靠纪律维持隔离的方案。
